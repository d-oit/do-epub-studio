# TRIZ core analysis — logout and offline persistence

**Status:** Resolved, implemented, and regression-proved (2026-10-20)
**Scope:** GOAP-1002 S1 local logout teardown; encrypted IndexedDB writers and the sync queue only.
**Evidence boundary:** Repository source plus local unit and browser evidence. Deployed behavior is not claimed.

## System properties

- Offline reader data is encrypted using the current session token and persisted in IndexedDB.
- Manual logout performs a best-effort server logout, clears encrypted stores and the `book-content` cache, then clears auth state.
- Auth-loss handling clears auth state before asynchronously purging encrypted stores.
- Several writer helpers await encryption before starting their IndexedDB write transaction.
- The sync queue checks session identity after some awaited operations, but not every persistence helper checks again at its commit boundary.

## Contradiction 1 — complete logout purge vs asynchronous persistence

**Improving:** Privacy and correctness of logout teardown: after sign-out, no old-session data remains or reappears in local stores.
**Worsens:** Availability of legitimate offline writes in a live session; an indiscriminate stop can reject an authored write that has not committed yet.
**Why:** `saveProgress`, `addToSyncQueue`, `saveBookFile`, `saveReadingInsight`, and related helpers await `encryptEntry` and then issue `db.put`. A logout purge can run during that await; without a final current-session check, the writer may issue its put after the purge transaction has cleared the store. `useReaderLogout` also currently clears data before it clears the auth token.
**Reality:** Real source-level interleaving, not yet reproduced at runtime. The async boundary and missing commit-time check are present in source; deterministic regression proof is still required.
**Type:** Technical contradiction.
**TRIZ principles available:** Segmentation (separate a session's writes from a later session), separation in time (invalidate the session before purge), dynamicity (check session validity at the persistence boundary).

## Contradiction 2 — stopping stale replay vs preserving current-session queue semantics

**Improving:** A logout or account switch must prevent old-session replay results from mutating local state or recreating queue data.
**Worsens:** Letting already-authorized requests complete may delay cleanup; aborting or discarding a write without a clear session boundary can make a legitimate current-session action appear saved when it was not.
**Why:** `attemptSync` awaits queue reads and network operations. It checks session identity at several continuation points, but a stale async database write can still be in progress at the point local teardown begins.
**Reality:** Stale reply guards exist; complete commit-boundary fencing is not established. No evidence supports changing server-side replay or signed-file policy.
**Type:** Technical contradiction.
**TRIZ principles available:** Separation in time (revoke local session before clearing), local quality (fence only writes tied to a stale session), partial action (cancel future retries without changing the queue contract for active sessions).

## Constraints for resolution

- Keep the current encrypted IndexedDB schema and encryption boundary.
- Do not alter signed URL TTL, server authorization, or offline access policy.
- Reject stale-session writes at their commit boundary; never fall back to plaintext.
- Clear all encrypted stores and book content cache on logout, while reporting purge failure honestly.
- Prove the late-write interleaving with a deterministic local test before claiming the source-level S1 race is closed.
- Keep cross-account ciphertext readability and deployed behavior explicitly unclaimed.

## TRIZ solution and component mapping

### Resolved: Contradiction 1 — complete purge vs asynchronous persistence

**Problem:** A delayed encrypted write can be issued after logout has cleared IndexedDB.
**IFR:** Logout removes all old-session rows and no old-session write can reappear, while writes in an unchanged active session remain available.
**Separation:** Time and condition — invalidate the local session before purge; each writer verifies that its captured token is still current immediately before its IndexedDB write.
**Solution:** Sensitive writers capture the session token before asynchronous work, re-check it after each await, and start the write request only if the same token remains current. Manual logout cancels scheduled sync retries, clears auth state, then purges encrypted stores and the book-content cache.
**Why better:** A commit-boundary fence rejects only stale-session work; it adds no store, queue, or persistence convention.
**New contradictions:** NONE. Logout already intentionally removes device-local reader data; stale writes now reject rather than silently repopulate it.

### Resolved: Contradiction 2 — stop stale replay vs preserve active-session queue behavior

**Problem:** An authenticated request or sync continuation can outlive its session transition.
**IFR:** No old-session replay continues locally after logout, without changing active-session retries or claiming that browser cancellation undoes a server-side operation already accepted.
**Separation:** Condition and time — bind active authenticated request controllers to the current session; a token change aborts those requests, and existing sync token/book checks stop stale continuations.
**Solution:** The API client tracks controllers without retaining bearer-token strings and aborts authenticated `apiRequest` and raw requests on session change. Logout cancels scheduled retry timers before auth invalidation; offline writer guards fence any late local continuation before it can commit.
**Why better:** Cancellation is scoped to authenticated requests from the replaced session. Existing queue ordering, retry policy, and server authorization remain unchanged.
**New contradictions:** NONE. A request already processed by the server may have taken effect before browser cancellation; this design makes no rollback or server-side cancellation claim.

**Component mapping:** `apps/web/src/lib/api/core.ts` owns authenticated-request cancellation; `apps/web/src/lib/offline/db.ts`, `annotation-mutations.ts`, and `feedback-drafts.ts` own commit-boundary checks; `useReaderLogout.ts` orders retry cancellation, auth invalidation, and purge. `plans/003-system-design.md` records these interfaces and limits.

**Verification (2026-10-20, local):** `apps/web/src/__tests__/logout-teardown.test.ts` releases a delayed-encryption sync write after the logout purge; the case was observed failing on the unguarded implementation and passes with the commit-boundary fence. `apps/web/src/lib/api/core.test.ts` proves both typed and raw authenticated fetches abort on a session change. `apps/tests/logout-device-data.spec.ts` proves the browser-level purge (`chromium` 1/1, `pwa-chromium` 1/1). Deployed behavior remains unclaimed.
