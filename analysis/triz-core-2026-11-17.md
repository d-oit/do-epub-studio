# TRIZ Core Analysis: Annotation Export and Author Preview Modernization

## System

The reader exports annotations into EPUB 2 or EPUB 3 packages, validates the exact generated bytes before download, and offers safe author previews that reflect the current draft and existing reader preferences. The implementation runs in a memory-bounded Cloudflare Worker and browser, preserves book and tenant isolation, and remains verifiable through existing test, CI, and plan-index workflows.

## System properties

- **Publication fidelity:** original package resources and metadata remain unchanged except the OPF/navigation entries required for the appendix.
- **Resource safety:** compressed input, expanded entries, annotation data, output ZIP, runner response, and validation time all have independent bounds.
- **Locator trust:** generated links resolve only through exact, unambiguous source spine/manifest entries and validated CFIs.
- **Validation assurance:** the downloaded bytes are the same bytes accepted by the configured EPUBCheck runner.
- **Preview fidelity:** a current draft can be inspected immediately, and existing reading preferences update a mounted EPUB rendition without repackaging.
- **Availability:** offline Markdown remains usable; server-dependent formats fail visibly when the API or validator is unavailable.
- **Historical accuracy:** completed plans can be archived without erasing open deployment, security, or evidence acceptance.

### Contradiction 1 — Technical: EPUB compatibility vs bounded processing

**Improving:** Preserve valid EPUB 2 and EPUB 3 package structure, navigation, metadata, and original resources while adding an annotation appendix.
**Worsens:** Worker memory, CPU, and request duration if the implementation inflates or retains an unbounded source, annotations, or generated archive.
**Why:** EPUB is a ZIP container whose declared sizes are untrusted; compatibility requires parsing source package/navigation XML, while safe re-export requires accounting for decompressed and output bytes.
**Reality:** Real. The Worker has a finite isolate memory ceiling, and malicious ZIP metadata or expansion can exceed it before a post-hoc size check.

**TRIZ Principles Available:**

- **1 — Segmentation:** metadata-only ZIP inspection precedes incremental inflation; each processing stage has its own byte/item cap.
- **3 — Local quality:** only the selected OPF and navigation documents are rewritten; other uncompressed resources stay byte-identical.
- **15 — Dynamicity:** count actual streamed bytes and abort as soon as a bound is crossed rather than trusting archive declarations.
- **16 — Partial or excessive action:** reject over-cap input/output explicitly instead of truncating or returning a partial EPUB.

**Status:** Resolved by the approved contract's independent source, expanded-size, entry-count, annotation, XML, and output limits, pre-allocation checks, incremental counting, and post-build structural validation. No cap is inferred from upload/archive limits.

### Contradiction 2 — Technical: useful annotation links vs untrusted stored locators

**Improving:** Link an exported note to the source location readers recognize.
**Worsens:** Security and correctness if a stored chapter path, bookmark JSON, revision, or CFI is used to construct an href without proving it belongs to this package and spine.
**Why:** Annotation rows may be stale, malformed, ambiguous, or from another publication revision; raw locator strings must not select archive paths or become unchecked URL fragments.
**Reality:** Real. The data model supports reanchoring and stale revisions, and user-controlled archive paths/CFIs cross a document-navigation boundary.

**TRIZ Principles Available:**

- **3 — Local quality:** resolve only through parsed manifest/spine entries and trusted package-relative paths.
- **10 — Preliminary action:** validate locator syntax, revision, spine membership, ID assertions, and bookmark shape before generating links.
- **23 — Feedback:** expose stale or ambiguous locations as visible unresolved markers rather than silently guessing.

**Status:** Resolved by exact manifest/spine matching, existing bounded CFI validation, revision checks, safe generated hrefs, and rendering every unresolved annotation without a guessed link.

### Contradiction 3 — Technical: validation assurance vs request latency and service availability

**Improving:** Ensure each downloaded EPUB is synchronously checked by the configured EPUBCheck runner and that its digest matches the exact returned bytes.
**Worsens:** Request latency and availability when the validator is slow, unavailable, returns malformed data, or processes a large valid package.
**Why:** Returning before validation or falling back to a local/mock result would improve responsiveness but would make success mean something weaker than the accepted contract.
**Reality:** Real. EPUBCheck is an external service boundary with network and processing failure modes; an unchecked export is not equivalent to a validated one.

**TRIZ Principles Available:**

- **1 — Segmentation:** keep archive safety, package parsing, runner validation, and response parsing as separate bounded stages.
- **10 — Preliminary action:** validate runner configuration and source limits before expensive reads; cap response bytes and apply one overall deadline.
- **15 — Dynamicity:** distinguish timeout, unavailability, invalid response, digest mismatch, safety rejection, and conformance errors.

**Status:** Resolved by fail-closed synchronous validation, a fixed validated runner origin, 130-second deadline, 300,000-byte response cap, digest/safety checks, stable error responses, and no persistence/queue fallback.

### Contradiction 4 — Technical: immediate author feedback vs parsing and packaging cost

**Improving:** Show the current in-memory chapter draft immediately and keep the full-book preview consistent with reader preferences.
**Worsens:** Main-thread responsiveness, asset traffic, and loss of preview position if every keystroke or preference change repackages the entire EPUB and recreates the rendition.
**Why:** The chapter editor changes faster than autosave, while the full preview uses the production EPUB parser and rendition.
**Reality:** Real. Autosave delay and EPUB packaging/parsing are distinct work; doing them on every edit or theme adjustment adds avoidable latency and can reset visible state.

**TRIZ Principles Available:**

- **1 — Segmentation:** render the edited allowlisted AST in an immediate chapter preview; reserve package generation for the explicit full-book preview action.
- **15 — Dynamicity:** defer and memoize AST parsing, update theme/direction on the existing rendition, and fetch only referenced image assets.
- **25 — Separation in time:** debounce/defer rendering work without waiting for the unchanged autosave timer.

**Status:** Resolved by safe AST rendering for the live chapter, explicit full-book packaging, stable asset URL ownership, and applying existing reader preferences to the current rendition without repackaging.

### Contradiction 5 — Technical: offline usefulness vs server-validated formats

**Improving:** Keep annotation export available when the reader is offline.
**Worsens:** Correctness if HTML/EPUB formats are offered as if they were available without authenticated API/validator access.
**Why:** Markdown can be rendered entirely from local annotation state; HTML and annotated EPUB require online API behavior, source retrieval, and (for EPUB) runner validation.
**Reality:** Real. The formats have different data and validation dependencies.

**TRIZ Principles Available:**

- **1 — Segmentation:** separate local Markdown from online server formats.
- **3 — Local quality:** keep Markdown's current renderer and round-trip contract unchanged.
- **23 — Feedback:** disable unavailable server choices and explain the missing online/session prerequisite.

**Status:** Resolved by preserving offline Markdown with zero network requests and explicitly disabling HTML/EPUB server export while offline or lacking the required book/session.

### Contradiction 6 — Technical: compact plan index vs preserved audit evidence

**Improving:** Reduce index noise by archiving completed GOAP records and compacting status notes.
**Worsens:** Traceability if a move loses path coverage, a historical note is mistaken for a committed file, or an open deployment/security acceptance is archived as complete.
**Why:** The repository shares ADR/GOAP numbering and records links across plans, docs, skills, and source comments; a move changes link depth and index paths.
**Reality:** Real. Existing root plans include open acceptance that must remain active, while closed plans may still be cited by exact paths.

**TRIZ Principles Available:**

- **1 — Segmentation:** archive only the enumerated completed batches; keep the explicit active-plan allowlist at root.
- **10 — Preliminary action:** validate plan headers and destination collisions before each move batch.
- **23 — Feedback:** require path-based index validation and local relative-link validation after every batch.

**Status:** Resolved by the explicit batch/keep lists, preserving ADRs and open acceptance, updating all inbound/outbound paths, and running plan validators between batches.

## Unresolved contradictions

None within the approved scope. Production deployment credentials, reachable Docker integration, and live external acceptance are environmental prerequisites, not reasons to weaken the fail-closed export or demo policy. No implementation or live verification is claimed by this analysis.
