# TRIZ Core Analysis — EPUB Conformance, Interchange, and Accessibility Issues

**Date:** 2026-10-31
**Scope:** Open GitHub issues #1414–#1419.
**Status:** All five contradictions resolved; component mapping is recorded in `plans/003-system-design.md`.

## System and parameters

The system is a Cloudflare Worker + D1/R2 upload and reader application, `reader-core` EPUB parser, web admin/reader, shared schemas, Playwright/Vitest tests, and CI. Relevant properties: standards coverage, request latency and memory, archive safety, report provenance, internal API stability, truthful accessibility evidence, fixture reproducibility, user confidentiality, and interoperability.

### Contradiction 1 — standards validation versus request-path safety and latency

**Improving:** Publication conformance coverage, especially for large EPUBs and EPUBCheck diagnostics.
**Worsens:** Worker request latency, memory pressure, and security if validation is moved into a privileged or unsafe process.
**Why:** The current upload path runs JavaScript EPUB checks synchronously for small files and skips them above 25 MiB; EPUBCheck is a Java tool, and a Cloudflare Worker cannot safely launch Java. Sending raw publication bytes to an unauthenticated or long-lived service would introduce data-exposure risk.
**Reality:** Confirmed by `apps/worker/src/routes/admin/books-upload.ts` and the official EPUBCheck CLI documentation, which requires Java and supports JSON output.
**Type:** Technical.
**TRIZ principles available:** Time separation, segmentation, extraction, local quality.

### Contradiction 2 — interoperable annotation export versus stable private storage

**Improving:** Interoperability with the EPUB Annotations Working Draft and round-trip preservation of locators/context.
**Worsens:** Stability and simplicity of the product's existing annotation store/API if draft terms are made its canonical model.
**Why:** The internal model carries CFI and multi-signal locator data under ADR-006; EPUB Annotations is a versioned Working Draft profile and may change.
**Reality:** Confirmed by current internal schema and W3C status metadata: EPUB Annotations 1.0 is a Working Draft, while the Web Annotation Data Model is a Recommendation.
**Type:** Technical.
**TRIZ principles available:** Segmentation, local quality, nesting, dynamicity.

### Contradiction 3 — machine-checkable accessibility evidence versus semantic certainty

**Improving:** Actionable publication metadata and structural checks, plus EPUBCheck diagnostics.
**Worsens:** Risk of false-positive/false-negative conformance claims if deterministic checks are presented as a complete accessibility audit.
**Why:** Metadata does not prove that alternatives, reading order, table relationships, or media equivalents are meaningful; semantic checks require human review.
**Reality:** Explicit in EPUB Accessibility 1.1's distinction between discoverability metadata and content conformance. Existing reader UI accessibility and publication accessibility also concern different surfaces.
**Type:** Technical.
**TRIZ principles available:** Segmentation, extraction, partial action.

### Contradiction 4 — representative regression coverage versus copyrighted or nondeterministic fixtures

**Improving:** Coverage of EPUB 2/3, emerging 3.4, layout, navigation, text direction, media, SVG, MathML, and accessibility features.
**Worsens:** Licensing/privacy risk and reproducibility if coverage depends on third-party books or external samples.
**Why:** A realistic corpus is useful, but committing copyrighted publications or personal data is disallowed, and downloading live samples makes CI unstable.
**Reality:** The issue explicitly prohibits copyrighted samples and requires deterministic generation; the existing `reader-core` suite already generates synthetic EPUBs from source.
**Type:** Technical.
**TRIZ principles available:** Segmentation, local quality, partial action.

### Contradiction 5 — expanded WCAG 2.2 evidence versus EPUB sandbox security

**Improving:** WCAG 2.2 AA impact evidence and route-level automated accessibility coverage.
**Worsens:** EPUB content isolation if test code injects scripts into the sandboxed publication frame; axe cannot prove manual assistive-technology behavior.
**Why:** The app-owned shell and the untrusted publication iframe need different testing methods.
**Reality:** Existing accessibility guidance documents the scripts-disabled iframe and axe scan boundary; WCAG 2.2 is a W3C Recommendation and the issue requires keyboard/NVDA or VoiceOver evidence without script injection.
**Type:** Technical.
**TRIZ principles available:** Segmentation, condition separation, extraction.

## TRIZ resolution

1. **Time/system separation:** EPUBCheck executes in an isolated Node/Java runner after the Worker request; the Worker persists a revision-scoped job and exposes retryable state. Existing archive safety checks remain an independent hard-rejection boundary.
2. **Segmentation/local quality:** Versioned EPUB Annotations JSON-LD is an adapter over unchanged internal annotation DTOs. EPUBCheck, automated accessibility checks, manual content review, and reader-UI accessibility remain separately labeled evidence.
3. **Extraction/partial action:** Report only deterministic metadata and structural findings as machine evidence; leave semantic alternatives, reading order, and real assistive-technology behavior explicitly unresolved until human review.
4. **Segmentation:** Build capability coverage from generated, deterministic synthetic EPUBs, each mapped to a named capability; no third-party book content or personal data enters the corpus.

**New contradictions:** NONE unresolved. An external runner requires deployment configuration, which is explicit and represented as pending/failed validation instead of a false passing report.
