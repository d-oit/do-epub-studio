# TRIZ Resolution — Issue #1432: EPUB Annotation Re-export

## Contradiction 1 — source fidelity versus bounded rewrite

**IFR:** The exported package retains all source publication resources and metadata, adds a readable annotation appendix and package references, and never exceeds independently enforced archive/annotation/output limits.

**Separation:** Condition separation. Bounded packages are transformed; over-limit inputs fail before decompression or output buffering.

**Solution:** Keep original chapter/resource bytes unchanged. Add one escaped XHTML appendix plus only the necessary OPF manifest/spine/navigation references. Preflight compressed bytes, actual uncompressed bytes, entry count, annotation bytes/count, and generated output bytes. Validate source and output archives.

**Why better:** Output is additive and navigable; large inputs produce an explicit limit error instead of unbounded Worker allocation or a partial artifact.

**Secondary contradictions:** None. Strict limits reduce availability for very large books; this is the explicit Worker-memory boundary.

## Contradiction 2 — source navigation versus untrusted/stale locators

**IFR:** Every annotation remains readable; links are emitted only when a locator resolves to a source item in the selected revision, and every other record remains marked unresolved with available chapter/text context.

**Separation:** Condition separation and segmentation. Trusted OPF manifest/spine data defines targets; user text is escaped into a distinct appendix.

**Solution:** Resolve `chapter_ref` only by exact normalized membership in the selected EPUB's manifest/spine. Accept CFI navigation only after bounded syntax validation and agreement with that spine target. Generate only relative package-internal hrefs. Orphaned, needs-review, stale-revision, malformed, absent, or ambiguous locations remain in the appendix with current/original chapter and quote context. Never fetch annotation URIs or resources.

**Why better:** Valid links navigate within the copied publication without rewriting source prose; uncertainty is visible rather than guessed or discarded.

**Secondary contradictions:** None. Some legacy/ambiguous locators remain unresolved because their source cannot be proved safely.

## Contradiction 3 — validation before response versus runner latency/availability

**IFR:** HTTP success means the exact returned bytes passed archive safety and EPUBCheck; runner failure can never become false success.

**Separation:** System/time separation. The existing isolated runner performs EPUBCheck synchronously for the bounded transient artifact; asynchronous upload validation remains unchanged.

**Solution:** Reuse the fixed `/validate` URL and bearer-token boundary. Bound the request and response, require accepted archive safety, parse the runner schema, compare its SHA-256 with the exact generated bytes, and reject EPUBCheck error findings. Return actionable validation/availability errors.

**Why better:** The Worker does not run Java, the returned bytes are validated before delivery, and upload/revision validation behavior stays unchanged.

**Secondary contradictions:** None. Runner outages make EPUB export unavailable; fail-closed is required by the acceptance contract.

## Contradiction 4 — offline Markdown versus server-authorized EPUB

**IFR:** Local Markdown remains available offline while EPUB export uses the current authenticated session, the authorized latest revision, and user-scoped server annotations.

**Separation:** System/condition separation. Preserve the current Markdown renderer/download; send HTML/EPUB through the authenticated API.

**Solution:** Add a localized accessible format selector. Keep the local Markdown path unchanged. Download HTML from the existing JSON response and EPUB from a bounded binary attachment. Keep the EPUB Annotations JSON interchange route separate.

**Why better:** New online capability does not regress local exports or conflate the distinct JSON feature.

**Secondary contradictions:** None. Online formats use the existing session/access controls.

**Status:** All four contradictions resolved; no secondary contradiction remains open.
