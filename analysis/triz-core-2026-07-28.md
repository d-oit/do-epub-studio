# TRIZ Core Analysis - d.o.EPUB Studio (Maturity Phase)

**Date:** 2026-07-28
**System:** d.o.EPUB Studio - Production EPUB reading and editorial
workspace. Mature monorepo (56+ ADRs, 0 open issues, all 28 swarm
gaps closed, ~130 GOAP plans archived).

**Supersedes:** `triz-core-2026-04-07.md` (5 contradictions from

## System Architecture Summary

- **Frontend:** PWA (Vite + React + Zustand + Tailwind), Workbox
  service worker, encrypted IndexedDB
- **Backend:** Cloudflare Worker (Hono), Durable Objects for rate
  limiting
- **Storage:** R2 (EPUB files via signed URLs), Turso (app state,
  11 tables, 7 migrations)
- **Auth:** Bearer tokens (localStorage), Argon2id, grant-based
  capability model, 7-day reader / 8-hour admin sessions
- **Sync:** Explicit queue with exponential backoff, LWW conflict
  resolution, zombie detection
- **Rendering:** EPUB.js fork in sandboxed iframe, DOMPurify
  allowlist, multi-signal CFI re-anchoring
- **Quality:** 500-line file limit, strict CSP, bounded regex
  (ADR-034), fail-closed gates (ADR-187)

## NEW Contradictions (Post-Maturity)

### Contradiction 1: Observability vs Reading Performance

**Improving:** Observability (traceId on every request, telemetry
events, audit logging, sync state tracking)
**Worsens:** Reading performance (critical rendering path latency,
memory overhead from event buffering)
**Why:** Every Worker request must emit traceId before the
path-length guard (AGENTS.md Tier 1). Telemetry events fire on
page load, navigation, EPUB open, annotation create, sync
complete. Audit logs append on every grant/session change. The
reader's first-paint-to-content-ready path includes: service
worker activation, Zustand hydration, IndexedDB permission check,
signed URL fetch, EPUB parse in Web Worker, rendition mount.
Adding telemetry and traceId generation to this chain increases
time-to-interactive.
**Reality:** Assumed: Observability always degrades performance.
Real: Async/non-blocking telemetry with batching and
`requestIdleCallback` can decouple observability from the critical
path. TraceId generation is O(1) nanoid overhead. The real
friction is synchronous audit logging on the Worker side, which
blocks the response.

**TRIZ Principles Available:**
- Dynamicity (batch telemetry, flush on idle or navigation)
- Segmentation (separate observability pipeline from request path)
- Prior action (pre-generate traceId in service worker before
  request reaches Worker)
- Skipping (fire-and-forget audit writes via Durable Object
  alarm, not inline)

### Contradiction 2: CSP Strictness vs WASM Capability

**Improving:** Content Security Policy strictness (no
`unsafe-inline` scripts, no `unsafe-eval`, only
`wasm-unsafe-eval`)
**Worsens:** WASM capability and third-party integration
(Argon2id client-side hashing, EPUB parser Web Worker, potential
future WASM-based features like CRDT merge)
**Why:** CSP `script-src 'self' 'wasm-unsafe-eval'` permits WASM
but blocks `eval()`, inline scripts, and dynamic `new Function()`.
Argon2id via `argon2-wasm-edge` requires WASM instantiation. EPUB
parsing in a Web Worker needs WASM for ZIP decompression. Any
future WASM module (e.g., CRDT engine, PDF export, image
processing) must conform to the CSP. Libraries that use
`eval()`-based dynamic loading break under this policy.
**Reality:** Assumed: CSP blocks all dynamic code. Real:
`wasm-unsafe-eval` was specifically designed for this use case.
The actual friction comes from: (a) inline styles needing
`style-src-attr 'unsafe-inline'` for React, and (b) any
third-party script that assumes `eval()` is available. Both are
solvable with proper module bundling.

**TRIZ Principles Available:**
- Nesting (WASM modules self-contained within Worker scope,
  CSP enforced at outer frame)
- Asymmetry (different CSP policies for different route scopes:
  strict for auth, relaxed for reader content)
- Extraction (extract WASM-heavy code into dedicated Worker
  origins with own CSP)
- Universality (use standard WebAssembly.instantiateStreaming
  which CSP already permits)

### Contradiction 3: Codebase Maturity vs Onboarding Velocity

**Improving:** Codebase maturity (56+ ADRs, comprehensive docs,
fail-closed gates, zero TODO/FIXME, strict 500-line file limit)
**Worsens:** Onboarding velocity (new developers face massive
context: architecture docs, security posture, GOAP methodology,
skill system, quality gates)
**Why:** The codebase has accumulated 56+ ADRs, 20+ docs files,
AGENTS.md with 4-tier compliance, skill-based workflows, GOAP
orchestration, and strict quality gates. A new contributor must
understand: monorepo structure, Turso/R2 split, signed URL flow,
grant-based auth, offline-first sync, EPUB rendering pipeline,
CSP constraints, bounded regex requirements, and the GOAP plan
lifecycle. This context wall slows initial contribution.
**Reality:** Assumed: More documentation always helps. Real:
Documentation has diminishing returns after a certain density.
What helps onboarding is: (a) a single "quickstart" path that
bypasses full context, (b) progressive disclosure of complexity
(scaffold first, deep-dive later), and (c) self-documenting code
with good naming over extensive external docs.

**TRIZ Principles Available:**
- Segmentation (separate "contributor quickstart" from
  "architecture deep-dive")
- Prior action (pre-built dev environment via Codespaces/Docker
  with all deps pre-installed)
- Nesting (layered docs: 1-page overview -> section guides ->
  full ADR index)
- Universality (standard patterns that don't need custom
  explanation: Hono routes, Zustand stores, Vitest tests)

### Contradiction 4: Deferred Infrastructure vs Deployment Readiness

**Improving:** Deployment readiness (production-quality code,
full test coverage, CI passing, zero known issues)
**Worsens:** Infrastructure completeness (production email
transport, telemetry endpoint, EPUB re-export)
**Why:** The codebase is code-complete for all P1/P2 features but
has 3 deferred infrastructure items: (a) production email
transport (magic links use logging mock), (b) authenticated
telemetry endpoint (client telemetry is in-memory only), (c) full
EPUB re-export (only Markdown/HTML export exists). These are
non-code blockers — the implementation exists, but the binding to
production infrastructure is deferred. The system cannot serve
production users until email transport is wired.
**Reality:** Assumed: Code-complete = deployable. Real:
Infrastructure bindings are deployment blockers, not code issues.
The contradiction is that building infrastructure bindings
requires production environment access (Cloudflare dashboard,
DNS, email provider API keys) which cannot be done in the
codebase alone.

**TRIZ Principles Available:**
- Segmentation (separate "code" from "infrastructure" deployment
  tracks)
- Prior action (define infrastructure requirements as a checklist
  in a runbook, not as code)
- Dynamicity (use feature flags to gate features that require
  missing infrastructure)
- Mediation (use intermediary services: Cloudflare Email Workers
  for email, Workers Analytics for telemetry)

### Contradiction 5: Local Development vs Production Parity

**Improving:** Local development experience (fast iteration, no
external dependencies, offline development)
**Worsens:** Production parity (local uses Miniflare/mocked
services, production uses real Turso + R2 + Durable Objects)
**Why:** Local development uses Miniflare for Worker simulation,
local SQLite for Turso, and mock R2 storage. Durable Object rate
limiting (`RateLimiterDO`) behaves differently in Miniflare vs
production. Background sync, service worker caching, and
IndexedDB encryption all depend on browser APIs that differ from
test environments. Tests use `pool: 'forks'` for isolation but
cannot fully simulate Cloudflare edge runtime.
**Reality:** Assumed: Local = production. Real: ADR-179
explicitly addresses this gap. The real contradiction is that
production parity requires external service access (Turso, R2)
which defeats the purpose of local-first development. The
resolution is accepting the gap and compensating with integration
tests that run against real services in CI.

**TRIZ Principles Available:**
- Segmentation (separate unit tests [local] from integration
  tests [CI with real services])
- Dynamicity (toggle between local and remote backends via env
  vars)
- Mediation (use Turso local replica mode for closer parity)
- Nesting (local dev uses Miniflare, CI uses Wrangler preview,
  staging uses production config)

## Summary: Contradiction Priority

| # | Contradiction | Priority | TRIZ Strategy |
|---|---|---|---|
| 1 | Observability vs Reading Performance | High | Dynamicity + Segmentation |
| 2 | CSP Strictness vs WASM Capability | Medium | Nesting + Extraction |
| 3 | Codebase Maturity vs Onboarding Velocity | Medium | Segmentation + Nesting |
| 4 | Deferred Infrastructure vs Deployment Readiness | High | Segmentation + Dynamicity |
| 5 | Local Development vs Production Parity | Low | Segmentation + Mediation |

**Rationale:**
- **#1 (High):** Directly impacts user experience. Every
  millisecond on the reading path matters. Observability is
  non-negotiable but must be async.
- **#4 (High):** Blocks production deployment. Email transport is
  a hard gate for invite-based access.
- **#2 (Medium):** Currently well-managed via `wasm-unsafe-eval`.
  Future WASM additions need CSP review.
- **#3 (Medium):** Affects team scaling, not current solo
  development. Address when team grows.
- **#5 (Low):** Documented in ADR-179. CI integration tests
  compensate. Not a daily friction.

## Verification

   synchronous in current implementation. TraceId generated via
   `crypto.randomUUID()` in middleware before path-length guard.
   Audit log writes use `ctx.waitUntil()` at all 27 call sites
   (fire-and-forget).

   'wasm-unsafe-eval'`; `style-src-attr 'unsafe-inline'` is
   required for React. No `eval()` in current deps.
