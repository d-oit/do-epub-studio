# TRIZ Core Analysis — EPUB Annotation Re-export

**Date:** 2026-11-09
**Scope:** GitHub issue #1432 — add an authenticated EPUB annotation re-export format without changing Markdown/HTML behavior or conflating it with the separate JSON interchange feature.
**Status:** Contradictions identified; resolve before implementation.

## System and parameters

The system is the existing authenticated Worker export route, D1 annotation/revision metadata, R2 publication bytes, shared schemas, reader UI, reader-core ZIP/locator helpers, archive-safety validator, and external EPUBCheck runner. Relevant properties: source fidelity, annotation recoverability, locator integrity, untrusted-content safety, bounded Worker memory, validation truthfulness, request latency, authorization, and offline reader behavior.

### Contradiction 1 — preserve the source publication versus bounded in-memory package rewriting

**Improving:** Add a navigable annotation representation while retaining the original EPUB's chapters, resources, and package metadata.
**Worsens:** Worker memory and request reliability if every original entry and the generated output are buffered without strict limits.
**Why:** The current EPUB ZIP writer accumulates output chunks and then copies them into a final `Uint8Array` (`packages/reader-core/src/packager/zip.ts`); the upload cap is 200 MiB and the general archive validator permits up to 1 GiB uncompressed. Those existing caps are too broad to imply safe memory usage for a second ZIP rewrite.
**Reality:** Confirmed by `apps/worker/src/lib/stream-body.ts`, `packages/shared/src/archive-validator.ts`, and `packages/reader-core/src/packager/zip.ts`. The conflict is real for large files, not for a deliberately bounded export.
**Type:** Technical.
**TRIZ principles available:** Segmentation, local quality, partial action, extraction.

### Contradiction 2 — direct annotation navigation versus untrusted/stale locators

**Improving:** Make each safely resolvable annotation navigate to its original chapter/CFI location.
**Worsens:** Link integrity and safety if database fields are copied into package paths, XHTML, or CFI fragments without proving that they resolve inside the selected EPUB revision.
**Why:** `chapter_ref`, `cfi_range`, and bookmark `locator_json` are stored annotation data; current export rendering escapes text but does not resolve locators against an EPUB manifest/spine. Revisions may also mark annotations `orphaned` or `needs_review` and retain original locator context.
**Reality:** Confirmed by the export route, annotation schemas, and migration 0023. A manifest/spine membership check and a safe unresolved representation can separate linkable from stale data.
**Type:** Technical.
**TRIZ principles available:** Segmentation, local quality, nesting, partial action.

### Contradiction 3 — EPUBCheck before response versus request latency and runner availability

**Improving:** Return only a generated EPUB that passes the supported EPUBCheck profile, with actionable validation failures.
**Worsens:** Export latency and availability when a Java validator is remote, slow, or unavailable.
**Why:** The Worker does not launch Java. Existing validation sends bytes to a token-authenticated external runner (120-second runtime limit, 100 MiB input cap) through a queue for uploaded revisions. The issue requires validation before the export response, so skipping validation or treating a runner outage as success would violate the requested contract.
**Reality:** Confirmed by `apps/worker/src/lib/epub-validation-queue.ts` and `apps/epubcheck-runner/src/server.ts`; the request-path tradeoff is real. The export must fail closed with a distinct actionable error if validation cannot complete.
**Type:** Technical.
**TRIZ principles available:** Time separation, extraction, segmentation, partial action.

### Contradiction 4 — local/offline Markdown export versus server-authorized EPUB export

**Improving:** Offer EPUB export from the authorized original revision and server-owned annotations.
**Worsens:** Offline export availability if all existing note export is redirected to the network.
**Why:** The current reader `useExportNotes` hook builds Markdown from the local reader store and downloads it without an API request; the Worker route uses `readerAuth`, `assertBookAccess`, and user-scoped D1 queries. Replacing the local path with a server-only call would break its offline behavior.
**Reality:** Confirmed by `apps/web/src/features/reader/hooks/useExportNotes.ts` and `apps/worker/src/routes/export.ts`. The formats can use separate backends while the local Markdown path remains unchanged.
**Type:** Technical.
**TRIZ principles available:** Segmentation, time separation, local quality.

## Design constraints carried forward

- Keep the internal annotations and EPUB Annotations Working Draft JSON interchange contract separate.
- Treat source size, uncompressed package size, annotation bytes/count, and final EPUB size as independent explicit limits.
- Validate package paths/locators against the selected revision; escape annotation text as XML/XHTML; never fetch URIs from annotation data.
- Preserve Markdown/HTML responses and the local offline Markdown download path.
- Do not claim EPUBCheck success on malformed output, validation errors, or runner failure.
